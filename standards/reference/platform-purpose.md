# Agent Platform의 목적과 설계 기준

사용자가 정의한 목적은 모델이나 범용 코딩 에이전트를 새로 만드는 것이 아니라,
Claude/Codex를 이용한 업무의 효율·흐름·조직 적합성·검토 가능성을 관리하는 것이다.
최종 판단과 책임을 가진 사람이 확인할 수 있는 근거를 제공한다.

| 목적 | 플랫폼이 제공해야 하는 것 | 판단할 지표·근거 |
|---|---|---|
| 사용 토큰 대비 효율 | 작업에 필요한 맥락·스킬 선택, 중복 요청 감소, 제한된 재시도·평가 | 검토를 통과한 업무당 총 토큰·시간, 실패·재작업·사용자 개입 횟수 |
| 전체 프로세스와 단계별 요청·검수 제어 | 작업 규모·위험에 맞는 단계, 입력·완료 조건, 검증된 handoff | 누락 단계, 미해결 요구사항, 차단 이유, 현재 코드와 연결된 검증 결과 |
| 회사 정책·도메인 적용 | 공통 정책과 프로젝트별 정책·용어·업무 규칙의 명시적 선택 | 적용한 정책 버전과 범위, 충돌·예외 및 검토 기록 |
| AI 업무가 제대로 수행됐는지 검토 | 요구사항→변경→검증→검토 근거 연결, 남은 불확실성 표시 | 요구사항별 수락 기준 충족 여부, 변경 diff, 테스트·리뷰 근거의 최신성 |

## 구현 원칙

- Claude/Codex의 파일 편집·도구 실행·기본 컨텍스트 관리 기능을 재구현하지 않는다.
  플랫폼은 작업 계약, 정책 선택, 단계 전환 조건과 검토 근거에 집중한다.
- 모든 작업에 모든 역할을 호출하지 않는다. 작은 작업은 기존 WORK 계약을 쓰고,
  역할 추가·다른 backend 검토·반복 평가는 얻을 검증 가치와 비용에 맞춰 선택한다.
- 토큰을 줄였다는 이유만으로 개선이라 판단하지 않는다. 동일한 업무·모델·평가
  조건에서 품질, 재작업과 사람의 개입을 함께 본다. 실패한 시도 비용도 포함한다.
  모델별 토큰 수는 직접 동등 비교하지 않고, 가격을 확인한 경우 비용을 별도로 본다.
- 실행 로그, 테스트 성공, 리뷰 승인, 요구사항 충족을 구분한다. 검증하지 못한
  항목은 unknown/not_run으로 남긴다. AI의 완료 선언만으로 승인하지 않는다.
- 정책은 코드·버전 관리 가능한 원본으로 유지하고, 변경은 diff·평가·검토를 거친다.
  자기 개선 후보를 자동 승인하거나 책임자의 판단을 대체하지 않는다.
- 관측은 검토에 필요한 증거를 제공한다. 원문 수집 여부와 보관 범위는 기존
  opt-in 정책을 따르며, 회사 데이터 전체를 기본 컨텍스트로 주입하지 않는다.

## 현재 기능과 후속 작업

현재는 작업 계약·역할 지침·gate/handoff·코드 상태에 연결된 검증 증거,
Claude/Codex 관측, 명시적 피드백과 개선 후보 평가·검토·적용 CLI를 제공한다.
이 기능들의 존재가 토큰 절감이나 업무 품질 향상을 입증하는 것은 아니다.

후속 개선 순서는 다음 기준으로 조정한다. 아래는 계획이며 구현 완료 주장이 아니다.

1. 완료 업무 단위로 최초 요청부터 재시도·검토·수정까지 비용과 근거를 연결한다.
   현재 run별 관측·평가 결과를 재사용하고 동일 사용량의 중복 합산을 막는다.
2. 단계마다 필요한 입력·정책·검증을 작게 정의하고 불필요한 맥락·역할 호출을 줄인다.
   어떤 맥락이 실제로 제공됐는지와 단지 설정돼 있는지를 구분한다.
3. 회사 공통 정책과 프로젝트 도메인의 버전·적용 범위·충돌을 명시한다.
   회사별 실제 정책 내용은 제공된 자료를 근거로 추가한다.
4. 최종 검토에서 요구사항별 변경·검증·미확인 사항을 한 번에 확인하게 한다.
   스킬 점검·설정 감사·checkpoint 개선은 이 네 목적에 기여하는 범위에서 진행한다.
